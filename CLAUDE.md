# CLAUDE.md — правила работы в этом репозитории

Источник истины по продукту и архитектуре — **SPEC.md**. Этот файл — короткая памятка, которую ты читаешь в начале каждой сессии.

## Как работать
1. В начале сессии прочитай `PROGRESS.md` (где остановились) и `DECISIONS.md` (что уже решено). SPEC.md перечитывай по разделам, относящимся к текущему этапу.
2. Работай строго по этапам SPEC §16. Не начинай следующий этап, пока текущий не прошёл критерии приёмки.
3. Не задавай вопросов: пробел в спецификации → разумное решение → одна строка в `DECISIONS.md` → продолжай.
4. После каждого этапа: `dotnet build` без предупреждений → миграции с нуля на пустую БД → `make lint` → `make test` → обнови `PROGRESS.md` → коммит (`stage N: <кратко>`).
5. Внутри этапа коммить логическими кусками (модуль/фича), чтобы откат был дешёвым.

## Жёсткие правила (кратко из SPEC §2, §4, §17)
- Стек зафиксирован (SPEC §2). Без AutoMapper, MediatR, FluentAssertions. Новая зависимость → причина в `DECISIONS.md`.
- Бизнес-логика только в `Dental.Domain` / `Dental.Application`. Эндпоинты тонкие, `DbContext` в эндпоинтах запрещён.
- Деньги — `long` в тиынах (`Money`), количества — `decimal`, время — UTC, отчёты по дням — в часовом поясе организации.
- Ничего не удаляем физически: `deleted_at`, отмена, сторно.
- Склад — только через журнал `stock_movements`; `stock_balances` — кэш в той же транзакции.
- Каждая бизнес-таблица — `organization_id` + `ITenantEntity` + query filter + RLS-политика.
- Ошибки — `ErrorCodes` + единый формат `{ error: { code, message, details } }`.
- Схема меняется только через новую EF-миграцию; применённые миграции не редактировать; после добавления — посмотреть `dotnet ef migrations script`.
- Падает тест → чини код, не тест (кроме случая, когда тест противоречит SPEC).
- `TODO` в коде допустим только с записью в `PROGRESS.md → Отложено`.
- Строки UI — только через i18n-ключи (`frontend/messages/ru.json`).
- Типы API на фронте — только сгенерированные (`make gen-types`), без ручных DTO.

## Запуск и проверка (SPEC §19)
- `start.bat` — поднимает инфраструктуру, собирает, мигрирует, сидит, запускает API и фронт, в конце вызывает проверку ролей.
- `check-roles.bat` — health, OpenAPI, фронт, вход под всеми 12 seed-пользователями, права/лимиты из `/auth/me`, 403 на запрещённых эндпоинтах. Отчёт — `.run/check-report.txt`.
- Конец каждого этапа: `check-roles.bat` (или `pwsh scripts/check-roles.ps1`) — 0 FAIL. Контракт API для скриптов — SPEC §19, не отступай от него.

## Окружение разработчика
- Разработка ведётся на **Windows**. `make` там может отсутствовать: помимо `Makefile` сделай `scripts/dev.ps1` с теми же командами (`up`, `migrate`, `seed`, `test`, `lint`, `gen-types`, `rebuild-balances`). Команды — через `dotnet` и `docker compose`, без bash-специфики.
- Testcontainers требует запущенный Docker Desktop.
- Line endings: см. `.gitattributes`; shell-скрипты и Makefile — LF.

## Известные подводные камни (учти сразу, зафиксируй в DECISIONS.md)
- **RLS и пул соединений.** Сессионный `set_config('app.org_id', …, false)` опасен при переиспользовании соединений. Предпочтительно ставить `set_config(..., true)` (transaction-local) в начале каждой транзакции, либо гарантировать сброс (Npgsql по умолчанию делает `DISCARD ALL` при возврате в пул — не включай `No Reset On Close`). Тест изоляции должен гонять запросы двух организаций попеременно на одном пуле.
- **Если `app.org_id` не задан**, политика RLS должна возвращать 0 строк (`current_setting('app.org_id', true)` + сравнение с NULL), а не падать и не пропускать всё.
- **Воркеры Hangfire и RLS.** Задачам нужно перечислить организации до установки тенанта: таблица `organizations` либо без RLS для роли приложения (только чтение id/timezone), либо отдельная роль/функция `SECURITY DEFINER`. Задачи Hangfire хранятся в своей схеме — исключи её из RLS.
- **Логин и RLS.** `users` и `memberships` нужны до выбора организации: `users` — глобальная таблица без RLS; выборку membership при логине делай через `SECURITY DEFINER`-функцию или отдельную политику по `user_id`.
- **`stock_balances` UNIQUE(warehouse_id, item_id, batch_id)** при `batch_id NULL` не сработает без `NULLS NOT DISTINCT` (PG 15+) — используй его.
- **Партиционированный `audit_log`**: первичный ключ обязан включать ключ партиционирования → PK `(id, created_at)`. EF-модель под это настроить, партиции создавать в миграции + ежемесячной задачей.
- **Exclusion constraint** для записей: два отдельных ограничения (по врачу и по креслу), `WHERE status IN (активные)`, диапазон `tstzrange(starts_at, ends_at, '[)')`; `chair_id NULL` не должен конфликтовать.
- **Нумерация документов** (`document_counters`): инкремент в той же транзакции, что и документ, — при откате номер откатывается, дыр нет. Цена — блокировка строки счётчика до коммита, поэтому номер бери в конце транзакции, а транзакции проведения держи короткими.
- **Idempotency**: при повторе с тем же ключом, но другим телом → 422 `IDEMPOTENCY_KEY_REUSED`.
- **Concurrency version**: инкремент в интерсепторе + клиент шлёт `version` → проставляй `OriginalValue`, иначе EF сравнит с загруженным значением и конфликт не поймается.

make rebuild-balances
